### ⭐ Q2：讲讲你的 RAG 是怎么实现的？为什么不用向量数据库？

**考察点**：是否真懂 RAG，还是只会调库。
**回答**：
> "流程是：字幕（真实抓取或内置演示）→ 分块 → 向量化 → 检索 → 生成。具体三步：
> **分块**：每块 240 字 + 20 字重叠，重叠是为了不让语义在边界被切断，块大小是成本和召回率的折中——块太大上下文浪费，太小语义不完整。
> **向量化**：为了零依赖可部署，我用了**哈希特征向量**（类似 hashing trick）：把分词后的词哈希到固定维度向量，加 TF 权重，再做 L2 归一化。它精度不如 embedding 模型，但完全离线、无 API 成本，个人项目里够用。
> **检索**：余弦相似度算 Top-K（K=3），把命中的片段带**视频名 + 时间戳 + 相似度分数**作为来源返回。
> **生成**：命中片段拼成上下文，system prompt 里写死'只根据片段回答、不足就说明、不要编造'，再交给 LLM 生成带引用的回答。
> 为什么不用向量数据库：个人项目要可移植、零部署，JSON 文件存储 + 内存检索足够了；**如果数据量上来或要做百万级召回，我会换成 pgvector 或 Chroma，检索接口我已经抽象成 vs.search()，替换成本很低**。"

### ⭐ Q3：Token / 上下文 / 推理，用你自己的话说说

**考察点**：概念理解是否扎实（JD 明确点名）。
**回答**：
> "**Token**：模型处理文本的最小单位，也是计费和窗口的计量单位。中文一个字约 1–2 token，我 RAG 分块 240 字大概 300–500 token，控制每轮问答的消耗。**上下文**：一次请求里模型能看到的所有内容（system + 历史 + 用户输入），窗口有上限，所以工程上要把**最相关的信息**放进去——我检索 Top-K 而不是把全部字幕塞进去就是这个原因。**推理**：模型基于上下文生成下一步 token 的过程，对我做工程的人来说，重点是**怎么用上下文和约束引导推理方向**——给足证据、明确格式、禁止编造，输出质量就稳。"

### ⭐ Q4：你怎么保证 LLM 输出的格式和稳定性？（Prompt Engineering 实战）

**考察点**：生产级 Prompt 能力，不是"会聊天"。
**回答**：
> "三层保障：**第一层，Prompt 契约**——我的跨境电商模块用 system prompt 硬性规定 JSON schema（字段名、类型、结构都写死），比如选品分析必须输出 summary/opportunities/risks/pricing/platforms/keywords 六个字段。**第二层，代码容错**——我写了 llmJSON 封装：从回复里正则提取 JSON 片段再 parse，解析失败返回 null，调用方自动回退演示模板，**LLM 崩了产品也不崩**。**第三层，防幻觉**——RAG 问答的 prompt 明确写'只根据提供的字幕片段回答，不足就如实说明'，宁可说不知道也不编造。这背后是同一个原则：**把 LLM 当不可靠组件，所有输出都要有校验和兜底**。"

### ⭐ Q5：MCP 是什么？你的 MCP Server 怎么实现的？和普通 API 有什么区别？

**考察点**：对岗位职责 3 的理解深度。
**回答**：
> "MCP（Model Context Protocol）是 Anthropic 推的**标准化工具协议**：让 LLM 客户端（Claude Desktop、Cursor）以统一方式发现和调用外部工具，相当于 LLM 世界的 USB-C。和普通 API 的区别：普通 API 是**人**调用的（前端调后端），MCP 是**模型**调用的——客户端通过 tools/list 发现工具，tools/call 传参数调用，模型自己决定调哪个工具、传什么参数。
> 我的实现：用官方 @modelcontextprotocol/sdk 的 McpServer + StdioServerTransport，注册了三个工具（analyze_channel / ask_video_content / generate_ideas），参数用 zod 做 schema 校验。关键设计是**业务逻辑在 core.js，HTTP 和 MCP 共用**——同一份分析能力，网页里是人点的，MCP 里是模型调的，两边结果完全一致。自测我写了个裸 JSON-RPC 客户端测试，完整走 initialize → tools/list → tools/call 流程，不用 Claude Desktop 也能验证协议正确性。"

### Q6：演示数据和真实数据是怎么切换的？

**考察点**：工程容错设计。
**回答**：
> "策略是**'有真实能力才用真实，否则静默降级'**。后端读环境变量或配置文件里的 YT_KEY/LLM_KEY：有 Key 就 try 真实 API，任何一步失败（无 Key、网络、403/401）都 catch 住回退到内置演示数据生成器，并带一个 note 字段告诉前端'当前是演示数据'。前端据此显示'演示/真实'标。这样：**开发无 Key 能跑、演示永不白屏、坏 Key 也能测出问题**。为了验证真实路径，我写了 mock-apis.js 模拟 Google/DeepSeek 的返回，'fake-key' 走通、'bad-key' 触发 401 走回退——真实代码路径全部实测过。"
